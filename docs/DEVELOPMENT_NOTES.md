# 개발 노트

코드 주석에서 뺀 개발 과정, 실측값, 설계 근거를 모아 둔 문서입니다. 상수 값을 바꾸기 전에 참고하세요.

## 구조 설계

- **기능별 패키지:** `game`, `capture`, `ocr`, `api`, `ui`, `debug`로 나눴습니다.
- **포트와 어댑터:** 외부와 닿는 부분(게임 화면, Tesseract, Open API, 로그 파일)은 `lumi/ports.py`의 인터페이스 뒤로 숨겼습니다.
  - `lumi/app.py`는 인터페이스만 쓰고, 실제 구현은 `build()`에서 설정으로 만들어 넘깁니다.
  - 테스트는 가짜 구현을 넘겨 게임이나 API 없이 전체 흐름을 확인합니다(`tests/test_app.py`).
- **설정 객체:** 사용자가 바꿀 값만 `lumi/config.py`의 `Settings`로 모았습니다.
  - OCR 임계값처럼 알고리즘에 붙은 상수는 근거와 같은 곳에 두려고 각 모듈에 남겼습니다.

## 매칭 감지

- `Player.log`에 매칭 완료 시 아래 두 줄이 몇 ms 간격으로 연달아 찍힙니다. 그래서 5초 안의 신호는 한 매칭으로 처리합니다 (`MATCH_DEBOUNCE_SECONDS`).
  ```
  [OnReceiveMatchingUpdate] MatchingComplete, matchPadding.userCount : 16
  [OnReceiveMatchingUpdate] matchingNotification : MatchingPadding, Matched
  ```
- 로그에는 플레이어 닉네임이 남지 않습니다 (본인 닉네임도 없음, 2026-11 확인). 그래서 팀원은 화면 OCR로만 알 수 있습니다.
- 일반 게임과 랭크 게임 모두 같은 로그가 찍힙니다.
- 게임을 재시작하면 로그가 처음부터 다시 쓰여서, 파일 크기가 줄면 처음부터 다시 읽습니다.
- 매칭 완료 직후에는 닉네임이 아직 화면에 그려지지 않았습니다. 실게임에서 10초 넘게 걸린 적도 있어 최대 15초 재시도합니다 (`OCR_RETRY_TIMEOUT_SECONDS`).

## 닉네임 칸 위치 (`lumi/capture/screen.py`)

- 처음 좌표는 "창 크기 대비 %"였고, 기준 스크린샷이 1920×1080 게임 화면 아래에 흰 여백이 붙은 1920×1716 이미지였습니다. 그래서 실제 2880×1800 화면에서 엉뚱한 곳을 캡처했습니다.
- 1920×1080(16:9)과 2880×1800(16:10) 화면을 비교해 규칙을 찾았습니다.

  | | 1920×1080 | 2880×1800 |
  |---|---|---|
  | 닉네임 카드 폭 | 268px | 약 403px (1.5배) |
  | 닉네임 세로 위치 (화면 중앙 기준) | +402px | +603px (= 402 × 1.5) |

  UI 배율은 `min(가로/1920, 세로/1080)`이고(2880×1800에서 가로 기준 1.5, 세로 기준이면 1.67), 배치 기준은 화면 중앙입니다. 21:9 울트라와이드는 아직 확인하지 못했습니다.
- **위치 미세 보정:** 위아래로 칸 높이만큼 넓게 캡처한 뒤 글자가 가장 많은 구간을 고릅니다.
  - 처음에는 "밝은 픽셀 비율"로 골랐는데, 닉네임 아래의 색깔 진행 막대(밝기 약 148)를 글자로 착각했습니다. 그래서 "옆 픽셀과 밝기 차이가 큰 지점 수"로 바꿨습니다. 가로로 균일한 막대는 이 값이 거의 0입니다.
  - 고른 구간 위아래 여유 1px(`WINDOW_MARGIN_RATIO` 0.08)가 가장 좋았습니다. 2px이면 정확도가 떨어졌고, 0이면 'y' 꼬리가 잘렸습니다.
- **창 모드:** 제목 표시줄과 테두리를 뺀 클라이언트 영역(pywin32)을 씁니다.
- **가려진 창:** 화면을 보이는 그대로 캡처하므로, 다른 창(VS Code 등)이 게임을 가리면 그 창을 읽습니다. 실제로 VS Code의 줄 강조 테두리를 `一一一一`으로 읽은 적이 있습니다.

## OCR (`lumi/ocr/`)

### 다국어
- 언어팩 하나로는 여러 문자 체계를 못 읽어서 eng, kor, jpn, chi_sim, chi_tra를 모두 돌리고, 언어팩마다 담당 문자만 신뢰합니다.
  - kor는 영문을 숫자로 읽습니다(`sooin` → `50010`, 신뢰도 93). 그래서 영문은 eng 결과를 씁니다.
  - jpn/chi는 영문 단어를 eng보다 잘 읽는 경우가 있습니다(`ya`: eng 0~50, jpn 70~90). 단어 전체가 영문이면 신뢰도를 0.9배 해서 사용합니다.
- **병합 후보에서 한글과 한자/가나를 섞지 않는 이유:** 섞으면 한자를 한글로 잘못 읽은 글자가 끼어듭니다(`藤田皮卡丘` → `ie田皮卡드`, `불법체류자엠마` → `量법체류자엠마`).
- jpn과 chi도 서로 섞지 않습니다. 가나 자리에 엉뚱한 한자가 끼어듭니다(`アンベリ了`).

### 전처리와 배율
- 확대 배율은 2배, 3배, 6배, 6배+이진화를 씁니다. 글자마다 잘 읽히는 배율이 다릅니다.
  - `ya발견`의 한글은 3배, 영문은 6배에서 잘 읽힙니다.
  - 2배는 `124qer123`처럼 숫자가 많은 닉네임 때문에 추가했습니다. 이 폰트의 `2`를 다른 배율에서는 `le`로 쪼개 읽었습니다.
  - 배율 조합은 테스트 이미지 전체(24칸)로 비교해서 골랐습니다. 4배+이진화는 `124qer123`을 맞히는 대신 `藤田皮卡丘`를 놓쳤고, 8배는 2배와 정확도가 같았지만 이미지가 커서 느립니다.
- 배율은 칸 높이 16px 기준입니다. 2880×1800에서는 칸이 약 21px라서 같은 배율이면 글자가 너무 커져 정확도가 떨어졌습니다(`藤田皮卡丘` → `BR出反卡`). 그래서 칸 높이에 반비례하게 줄입니다.
- 오른쪽 끝의 UI 테두리가 `|`로 읽혀서 잘라냅니다. 열 전체 최솟값이 70을 넘으면 테두리로 봅니다.

### 속도 (Windows)
- Windows는 Tesseract 1회 실행 비용이 커서, 칸당 15회를 다 돌리면 한 번 시도에 약 7초가 걸렸습니다.
- 그래서 다음과 같이 줄였습니다.
  - 빈 칸(흰 글씨 픽셀 비율 5% 미만)은 OCR을 생략합니다. 측정값은 닉네임 칸 0.10~0.33, 빈 칸 0~0.03이었습니다.
  - 1단계(3배, eng/kor/jpn)에서 90점 이상이면 바로 확정합니다.
  - 그 결과 칸당 실행 횟수가 쉬운 닉네임 3회, 빈 칸 0회가 됐습니다.
- `OMP_THREAD_LIMIT=1`이 필요합니다. 병렬 실행 중 Tesseract 내부 스레드가 CPU를 두고 경쟁하면 크게 느려졌습니다(테스트 이미지 OCR이 500초 넘게 걸리던 것이 약 9초로).

### 한자 보정
- 획이 많은 한자는 작은 화면에서 뭉개집니다. 원본 크롭(201×21)으로 96가지 설정을 시험했더니 `藤`이 나온 건 1번(신뢰도 38)뿐이었습니다. 나머지는 대부분 `騰`/`滕`/`腾`/`朋`/`腺`/`腰`로 읽혔습니다.
- 그래서 직접 읽기보다 후보를 보정합니다.
  1. **위치별 투표:** 한자/가나 언어팩 결과를 x 위치로 묶어 가장 많이 나온 글자를 고릅니다. 신뢰도가 낮아도 버리지 않습니다(`田皮卡丘` → `滕田皮卡丘`).
  2. **비슷한 글자 치환:** 일반 후보로 못 찾았을 때만 `CONFUSABLE_GROUPS` 안에서 바꿔 조회합니다(`滕田皮卡丘` → `藤田皮卡丘`).
- 그룹에는 실제로 관찰된 것만 넣었습니다(`县`은 2배 확대에서 중국어 언어팩이 `藤` 대신 읽은 글자). 새로운 한자 닉네임을 못 읽으면 디버그 크롭으로 확인해서 추가하세요.

### PP-OCR로 교체 (`lumi/ocr/paddle.py`, 2026-11-05)
- Tesseract가 획 많은 한자(`藤`)를 직접 못 읽고, 2880×1800의 숫자 닉네임(`124qer123` → `14ロ3`)도 틀려서 PaddleOCR 인식 모델과 비교했습니다(`python -m lumi.debug.compare_engines debug`).
  - PaddlePaddle 본체는 Python 3.14 Windows 패키지가 없어 RapidOCR(ONNX)로 돌립니다.
  - 칸 하나가 한 줄이라 검출(det) 모델 없이 인식(rec) 모델만 씁니다. 입력 높이 48px로 맞춥니다.
- 비교 결과 (정답 있는 25칸, 1순위 정답 수, 칸당 중앙값, 다운로드 뺀 로드 시간)

  | 엔진 | 정답 | 칸당 | 로드 |
  |---|---|---|---|
  | Tesseract (기존 방식) | 20 | 1216 ms | – |
  | v5-korean (mobile) | 20 | 176 ms | 0.5초 |
  | v5-ch (mobile) | 16 | 75 ms | 0.6초 |
  | v5-ch (server) | 15 | 1964 ms | 3.6초 |
  | v4-japan | 4 | 280 ms | 0.9초 |

  - v5-korean은 한글+영문/숫자, v5-ch는 한자+가나+영문을 잘 읽고, 서로의 담당 문자는 빈 문자열이나 엉뚱한 글자를 냅니다.
  - server 모델은 mobile보다 낫지 않고 느립니다. v4-japan은 앞에 공백/`.`을 붙이고 한글 칸을 엉뚱하게 읽어서 뺐습니다. 가나는 v5-ch가 읽습니다(가나 샘플은 `アンベリィ` 1칸뿐이라 더 모아야 함).
  - 메모리: 모델 4개 로드 시 약 +200 MB (44 → 247 MB).
- **결과 고르기:** 점수가 높은 쪽을 고르면 `ya발견`을 ch의 `ya`(0.91)로 고릅니다(korean은 `ya발견` 0.87). 그래서 글자 종류로 고릅니다.
  - korean 결과에 한글이 있으면 korean, ch 결과에 한자/가나가 있으면 ch, 둘 다 아니면(영문/숫자) 점수로 고릅니다.
  - 담당 문자가 아닌 모델의 결과는 30점 깎아 API 조회 범위(1등과 25점 이내) 밖으로 뺍니다. `ya`가 실존 유저면 다른 사람이 확정되기 때문입니다.
- **정리:** 닉네임엔 공백이 없어서 공백을 지우고 앞뒤 `.`도 지웁니다(` PuniPaw`, `....PuniPaw`).
- **보조 후보(-10점):** 넓은 글자 옆 끝의 `1`/`I`/`l`/`|`를 뗀 후보, 한자 옆 세로선을 `丨`로 바꾼 후보(`静戒IBS` → `静戒丨BS`).
  - Tesseract와 같이 좌우 밝은 테두리를 먼저 잘라내서 `1얼음마녀`는 실제로는 나오지 않습니다.
- 결과: 1순위 정답 24/25, API 조회 후보 포함 25/25, 칸당 약 200 ms(모델 두 개). 실게임 `debug/` 크롭의 `124qer123`도 맞힙니다.
- **빈 칸 생략 기준을 0.02로 낮췄습니다** (Tesseract는 0.05). 실게임 2880×1800에서 두 글자 닉네임 `르채`가 흰 글씨 비율 0.046이라 빈 칸으로 생략됐습니다. 빈 칸은 최대 0.036이었고, PP-OCR이 빈 칸을 읽어도 점수가 35 미만(`1`, `…`, `↑–`)이라 읽힌 칸으로 치지 않습니다.
- RapidOCR는 첫 호출 때 모델을 로드해서, 첫 매칭에서 1.5초가 더 걸렸습니다. 만들 때 빈 이미지로 한 번 돌려 미리 로드합니다.
- `LUMI_OCR_ENGINE=tesseract`로 기존 방식으로 돌아갈 수 있습니다. rapidocr가 설치되지 않았으면 자동으로 Tesseract를 씁니다.

## 다른 유저 오매칭 방지 (`lumi/api/resolve.py`)

이터널 리턴 API는 닉네임이 정확히 일치해야 조회되는데, 잡음 후보가 우연히 실존 유저와 일치하는 일이 실제로 있었습니다.
- `静戒丨BS`의 일부만 읽은 `1BS`
- UI 가로선을 읽은 `一一一一`

그래서 다음 칸과 후보만 조회합니다.
- **확실히 읽힌 칸만 조회합니다**(`slot_ready`): 75점 이상, 또는 6글자 이상이면서 60점 이상.
  - 오매칭이 있었던 잡음은 모두 짧았습니다(`fis`, `和一`, `1BS`). 긴 닉네임은 우연히 일치할 가능성이 낮아 기준을 낮췄습니다(`124qer123`은 60점대).
  - 덜 읽힌 칸은 읽은 글자 그대로 "조회 실패" 카드가 되어 모달에서 고칠 수 있습니다.
- **게임 창이 가려진 동안은 캡처하지 않습니다.** 실게임에서 가려진 상태로 읽은 `fis`, `和一`이 실존 유저와 일치한 적이 있습니다.
- 점수 60 이상이고, 1등 후보와 25점 이내인 후보. 정답 후보는 최저 79.5점, `1BS`는 35점 미만이었습니다.
- 두 글자 이상인 후보. 같은 글자 반복이나 선 모양 문자만 있는 후보는 아예 만들지 않습니다.
- 비슷한 글자 변형은 세 글자 이상인 닉네임에서만, 최대 6개까지만 조회합니다.

## 게임 시작 감지 (`lumi/game/match_flow.py`)

- 닉네임 칸의 배경(맨 윗줄과 아랫줄 픽셀)을 매칭 직후의 기준 이미지와 비교합니다.
  - 같은 매칭 화면은 0, 닉네임만 다른 매칭 화면은 3~14, 로비가 아닌 화면은 50~85였습니다.
  - 이 값을 근거로 기준값을 30으로 잡았고, 3초 연속 넘으면 닫습니다.
- 게임 창이 가려진 동안(alt+tab 등)은 판단하지 않습니다. 화면을 보이는 그대로 캡처해서, 실게임에서 alt+tab 하자 앞에 온 창을 보고 '게임 시작'으로 닫혔습니다(2026-11-05).
- 실게임에서 캐릭터 선택 중에 일찍 닫히거나 안 닫히면 `LOBBY_GONE_DIFF`, `LOBBY_GONE_CONSECUTIVE`를 조정하세요.

## 모달 (`lumi/ui/overlay.py`)

- Qt 좌표는 Windows 배율이 적용된 논리 좌표입니다. 2880×1800 + 배율 200%는 논리 1440×900이라, 처음의 고정 좌표 `move(1500, 50)`에서는 화면 밖에 떠 안 보였습니다. 그래서 현재 모니터의 사용 가능 영역 기준으로 오른쪽 위에 놓습니다.
- 뜰 때 게임 포커스를 뺏지 않도록 `WA_ShowWithoutActivating`, 작업 표시줄에 안 뜨도록 `Tool` 창을 씁니다.

## 최근 게임 통계 (`lumi/api/recent_stats.py`)

- `/v1/user/games`는 한 페이지에 20게임보다 적게 줘서 `next` 커서를 따라갑니다. 20게임에 보통 3페이지가 필요했습니다.
- TK는 `teamKill`(팀 전체 킬)입니다. 개인 킬(`playerKill`)이 아닙니다. 전적 사이트의 TK 표기와 같습니다.
- 집계 대상은 일반+랭크 게임입니다. 코발트 프로토콜 등은 딜량과 킬 기준이 달라 뺐습니다.
